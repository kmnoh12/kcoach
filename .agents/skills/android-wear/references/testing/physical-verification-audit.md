# Physical verification audit recipe

Use this reference when auditing a phone↔Wear implementation before simplifying it or calling it Watch-validated. The goal is to distinguish implementation/runtime evidence from physical sensor evidence.

## Evidence ledger

Record these gates independently; never upgrade one from another:

1. current source and line-level control flow;
2. JVM/unit and instrumented/connected test coverage;
3. freshly assembled artifacts;
4. exact installed artifact identity;
5. target identity (physical Watch vs emulator);
6. command/session and service state transitions;
7. sensor registration and observed callbacks/samples;
8. transport path (production Wearable Data Layer vs emulator relay);
9. phone validation, analysis, persistence, ACK, and cleanup;
10. user-visible result/tempo/form rendering;
11. physical Watch accuracy/robustness.

## Repeatable audit sequence

1. Read manifests, service/activity code, shared wire/capture code, tests, and validation docs before running anything.
2. Trace both transport lanes explicitly. Search for `DataClient`/`Asset` and `MessageClient` separately from emulator bridge/TCP code. A relay success is not Data Layer Asset success.
3. Enumerate tests and Gradle source sets. A Kotlin/JVM `core` module with `src/test` proves pure logic only. Record `NO-SOURCE` for Wear unit-test tasks and absence of `androidTest`/connected tests rather than summarizing all Gradle success as device coverage.
4. Identify targets with `adb devices -l`, then classify each using model, product/device, build fingerprint, and API level. If only `sdk_*`, `generic`, `goldfish`, or `emulator-*` targets exist, physical-sensor evidence is unavailable.
5. Check target package state with `dumpsys package`: version code/name, update time, permissions, and stopped/installed state. Pull the installed `base.apk` from `pm path` and compare SHA-256 with the freshly built APK; this proves artifact identity, not behavior.
6. Check runtime state with focused activity, process/service dumps, sensor-service registrations, and fresh logcat. Confirm the Watch workout service is alive and sensor listeners are registered during WORKING, then confirm callbacks/sample count. A capture file or fake rep count without callback evidence is insufficient.
7. Follow one capture end-to-end: command/session start → sensor registration → samples → set completion → local raw-file/manifest persistence → phone receive/validation → analysis invocation → analysis persistence → ACK → watch cleanup. Capture IDs and session/set IDs must remain stable across logs.
8. Treat explicit emulator markers as scope labels. `isEmulator`, `emulator=true`, a host relay, synthetic ticker, or a log such as `sensorEvents=0` means emulator/lifecycle evidence only; it cannot support a Watch8 accuracy claim. A run with `sensorEvents=0` may still prove that generated bytes traverse validation and analysis, but not that physical sensing worked.
9. For UI claims, inspect the actual broadcast/Intent extras and result-card rendering, not only model fields. Verify tempo, wrist metrics, and form fields survive type conversion, persistence, restore, and display. A legacy `formScore` field being present does not mean a non-null biomechanical form result exists; capability contracts may intentionally leave it null and use wrist-feedback fields instead.
10. Report the strongest verified statement and the first unverified gate. Use labels such as `unit-tested`, `artifact-installed-on-emulator`, `emulator-relay/runtime-verified`, `production-Data-Layer-unverified`, and `physical-Watch-unverified`.

## Useful runtime interpretations

- `emulator capture received` → emulator relay payload reached the phone.
- `CAPTURE_VALIDATED` → manifest/bytes passed the phone validator.
- `ANALYSIS_STARTED`/`ANALYSIS_FINISHED`/`RESULT_SAVED` → phone analysis lifecycle ran and an encoded result was persisted.
- `CAPTURE_ACK_SENT`/`CAPTURE_ACK_RECEIVED` → ACK path ran; still distinguish relay ACK from production Data Layer ACK.
- `GooglePlayServices ... SERVICE_INVALID` or missing Play Store on a generic emulator → the observed flow likely depended on the explicit relay lane, not a proven production Wearable connection.
- `sensorEvents=0` → no observed sensor callbacks in that run; do not infer that capture bytes came from sensors.
- Bundle `ClassCastException` at a result receiver (for example, writing an integer and reading it with `getDoubleExtra`) → result persistence may succeed while some UI field handling fails. Treat the result screen as only partially verified until the type mismatch is fixed and re-run.
- Wear UI showing reps/heart rate/live phase but no final analysis card → final tempo/form/results are phone-side concerns and remain unverified unless phone UI evidence is captured.

## Reporting template

```text
Verified:
- source path and line facts
- exact test tasks and outcomes
- target identity and installed APK hash match
- observed command/runtime/capture/analysis/ACK events

Emulator-only:
- fake ticker or relay path
- synthetic/replay fixtures
- emulator capture counts and result persistence

Unverified:
- physical Watch sensor callbacks and sampling/batching
- real Watch Data Layer Asset transfer
- screen-off/recreation/permission/timeout behavior on hardware
- accuracy against manual/video ground truth
- non-null tempo/form values actually rendered

No source files modified; note any generated build/test artifacts separately.
```
