# 폰·워치 실기기 검증

2026-10-14: 실제 Watch8 기록과 횟수를 확인할 영상은 아직 없다고 사용자에게 확인했다. 아래 실기기 시나리오는 모두 **미실행**이다. Robolectric의 서비스 재생성 검사는 실제 화면 꺼짐·Bluetooth·Doze·기기 재부팅 검사를 대신하지 않는다. 현재 작업은 PLAN.md의 ADB 미사용 원칙을 따른다.

## 연결 전 준비

폰과 워치가 모두 같은 소스의 검증용 빌드인지 확인한다. 빌드 파일의 SHA-256과 앱 버전, 실제 설치한 파일을 별도로 기록한다. 빌드 성공은 설치 성공이 아니며, 설치 파일을 확인하지 못하면 일치 여부는 미확인으로 남긴다. Bluetooth 켜짐도 실제 Data Layer 통신 성공의 증거가 아니다.

원본과 검증 자료는 앱의 선택한 촬영 내보내기를 통해 회수한다. 기존 tools/device_check.py는 과거 ADB 진단 도구이며 이번 작업의 필수 절차로 실행하지 않는다. 폰/워치 데이터 삭제나 초기화로 실패를 숨기지 않는다.

새 규약을 검사하려면 폰과 워치 모두 이번 코드로 빌드한 앱이어야 한다. 사용자는 2026-10-14
“기존 앱 업데이트로 먼저 배포”라고 검증용 선행 배포를 승인했다. 검증용과 최종 배포는 모두
tools/release.sh를 사용한다. 실기 검증이나 실제 계정 호출 없이 전체 완료로 표시하지 않는다.

이전 준비 검사(0.7.3/0.2.4 버전 번호 유지 당시)의 로컬 서명 빌드: phone/build/outputs/apk/ota/phone-ota.apk(59,947,204바이트),
wear/build/outputs/apk/ota/wear-ota.apk(818,372바이트). 두 APK 서명은 검증됐으며 자세한 SHA와 버전은
reviews/2026-10-14-stage5-preparation-verification.json에 있다. 실제 설치·기존 설치본과의 인증서 일치는
미확인이다. 이는 당시의 과거 검사 결과이며 현재 배포 증거가 아니다.
기존 공개 APK 두 개와 준비 APK의 서명 인증서는 동일함을 확인했다. 기기에서 업데이트·기록 유지까지 확인한 것은 아니다.

공개된 [검증용 버전](https://github.com/kmnoh12/kcoach/releases/tag/p0.7.4-w0.2.5)은
폰 0.7.4(34)·워치 0.2.5(33)다. 두 앱의 latest 업데이트 URL과 실제 APK의 버전·해시·서명을 확인했다.
공개 확인은 `reviews/2026-10-14-validation-update-publication.json`에 기록했다. 두 기기의 `업데이트 확인`으로
업데이트한 뒤 폰은 메뉴, 워치는 운영체제의 앱 정보에서 버전을 확인한다.
현재 워치 앱 화면 자체에는 버전 표기가 없다. 기존 앱 삭제·저장소 초기화는 하지 않는다.

## 동시 촬영과 개인 보정 확인

1. 폰의 `메뉴 → 측정·보정`에서 촬영 버튼이 활성화된 컬·레이즈·삼두 운동을 선택하고
   `워치와 함께 영상 촬영`을 누른다. 촬영 화면에서 운동·착용 손·워치 방향을 확인하고
   `워치와 함께 촬영 시작`을 누른다. 어깨·팔꿈치·손목·몸통이 보여야 한다.
   현재 스쿼트 등 수동 대상은 이 진입 버튼이 비활성화돼 있으며 동시 촬영 검증 대상에 포함하지 않는다.
2. 준비 동작과 실제 반복을 촬영한 뒤 `촬영 종료 · 저장`을 누른다. 목표 횟수 도달만으로 촬영을 자르지 않는다. 0회는 실제 0회로 확인하고, 횟수 미입력을 0회로 취급하지 않는다.
3. `저장한 촬영 확인`에서 영상·워치 원본·시계 정렬 상태를 확인한다. 사람이 총 횟수와 시작·반환·복귀를 확인하며, 가림·화면 밖·시간 오차가 큰 구간은 제외한다.
4. 확인한 학습 자료로 후보를 만든 뒤 새로운 자료를 촬영한다. 후보 생성 전 자료를 같은 후보의 독립 검증에 재사용하지 않는다. 실제 20세트·3 UTC 날짜·150회와 품질·개수·경계·반응 기준을 모두 확인한다.
5. 고정 회귀 자료와 직전 실제 활성 모델을 비교한 뒤 채택을 요청한다. 워치 수신(STAGED)과 실제 센서 사용(APPLIED)을 구분하며, 세트 도중 모델을 바꾸지 않는다.
6. 이전 모델 복원과 `기본 측정` 복귀를 확인한다. 기본 측정 복귀는 다음 세트의 실제 기본 엔진 처리(DISABLED) 후 완료된다. 잘못된 학습 라벨을 수정했어도 보정 끄기는 가능해야 한다.

새 촬영의 세션 ID는 `paired-`이며, 과거 실측 보정의 `calibration-`과 구분한다. 촬영 자료에 포함된 모델 사용 여부·샘플 호출 수는 실제 원본과 비교한다. 카메라 관측각과 영상평면 편차는 추정 관측값이며 자세 정확도 점수나 임상 관절 ROM 검증으로 해석하지 않는다.

## 실기기 시나리오

워치 시작 추가 확인: 폰에서 루틴을 선택한 뒤 운동을 시작하지 않고 워치의 `워치에서 루틴 시작`을
누른다. 착용을 확인하거나 보정 없이 시작하고, 폰 확인 전에는 시간이 시작되지 않는지 확인한다.
수동 대상에서 실제 0회 입력·완료→휴식→`휴식 끝내고 다음 세트`를 확인한다. 연결이 끊겼을 때의
요청 보관·재연결·중복 입력·30분 만료도 각각 기록한다. 아래 실기 검증과 함께 아직 미실행이다.

| 순서 | 조작 | 확인할 결과 | 상태 |
|---|---|---|---|
| 1 | 폰에서 운동 시작, 워치에서 센서 기록·반복 수 확인 | 같은 세션/세트/시도 ID, 실제 측정된 심박만 표시 | 미실행 |
| 2 | 폰 화면을 끄고 워치에서 세트 완료, 휴식 만료까지 유지 | 완료 저장·휴식·다음 세트 진행, 화면 복귀 후 중복 완료 없음 | 미실행 |
| 3 | 운동 중 연결을 끊고 워치에서 완료, 연결 복구 | 워치의 반복/센서 기록 유지, 완료 ACK까지 재전송, 폰에 한 번만 반영 | 미실행 |
| 4 | 세트 삭제·되돌리기, 같은 세트 완료 취소 후 다시 측정 | 표시 번호가 바뀌어도 같은 세트 유지, 이전 시도 결과는 새 수행값을 보정하지 않음 | 미실행 |
| 5 | 같은 운동을 두 위치에 넣고 번갈아 선택 | 각 위치의 세트 선택과 반복 수가 서로 섞이지 않음 | 미실행 |
| 6 | 폰 앱을 실제로 종료한 동안 워치가 센서 기록 전송, 폰 앱을 다시 직접 실행 | 기존 DataItem도 다시 읽어 원본 저장 후 ACK, 분석 복구 및 완료 기록 보정 | 미실행 |
| 7 | 일시정지·휴식 중 워치 서비스 재생성, 이어서 별도로 워치 전체 재부팅 | 체크포인트에 저장된 반복·센서 조각·휴식 상태 복원, 폰 SYNC 후 일치 | 미실행 |
| 8 | 완료 기록 저장 후 늦게 네이티브 분석 완료 | 실제 수행 횟수·볼륨·이력 수정, 사용자 수동 입력 유지, 같은 날 다른 운동 보존 | 미실행 |
| 9 | ACK 후 연결 끊김/복구, 다음 운동 종료까지 유지 | 워치 전송 사본·DataItem 정리 재시도, 폰 원본과 분석 보존, 대기 중 불필요한 heartbeat 종료 | 미실행 |
| 10 | 여러 운동 후 용량 보고서 수집 | 폰 `missingFiles=0`, 워치 `missingQueuedFiles=0`, `missingRuntimeChunks=0`, `captureRecoveryRequired=false`, 전송 대기 해소, 실패 원본 보존. `incompleteCaptures>0`이면 격리 기록 사유를 확인 | 미실행 |

`force-stop`은 단순 프로세스 종료와 다르다. 강제 중지된 앱이 사용자가 다시 열기 전까지 자동으로 깨어나는 것을 합격 조건으로 삼지 않는다. 기기 재부팅과 Robolectric 서비스 재생성도 별도 항목이다. 종료 직전 체크포인트에 포함되지 않은 샘플/미완료 동작은 보장하지 않는다.

## 기록과 판정

선택한 검증 자료 ZIP을 회수하면 프로젝트 루트에서 다음 명령으로 무결성과 센서 메타데이터를 확인한다.

```sh
python3 tools/inspect_measurement_export.py '/실제/내보낸-촬영.zip'
```

파일을 추출하거나 엔진을 적용하지 않고 JSON을 출력한다. 잘못된 원본 해시·다른 시도·누락 파일이면
종료 코드 2로 실패한다. `reviewedReps: null`은 미확인이며 실제 0회와 다르다. ZIP 해시가 맞아도 실제
기기 설치·영상 코덱/PTS·시계 정렬·정확도·반응 지연은 별도로 검증해야 한다. 테스트용 합성 ZIP은 실기 자료가 아니다.

각 시나리오에 폰/워치 모델·OS, 설치 APK SHA-256, 실제 조작 시각, sessionId/setId/attemptId/captureId와 관찰 결과를 기록한다. 실패 시 로그의 `KCoachEvent`와 앱 저장 상태를 함께 비교한다. 로그만으로 화면 동작이나 Bluetooth 복귀를 통과 처리하지 않는다. 배터리 평가는 시작/종료 잔량과 동일 시간·조건을 함께 남긴다. 현재는 실제 기기의 소모량을 측정하지 않았다.

앱 내보내기의 원본 해시·시계·확인 라벨·상태와 실제 화면 관찰을 함께 보관한다. 보고서를 회수하지 못하면 미확인으로 남긴다. 계정 토큰이나 전체 SharedPreferences를 진단 자료로 내보내지 않는다.

폰 보고서: 센서 기록 수, 전체 파일 바이트, 실패·미확인 기록 수, 누락 파일, 참조되지 않은 파일, 완료 snapshot 용량 추정. 워치 보고서: 전송 대기 수, 누락 원본/manifest, DataItem 정리 대기 수, 전체/미확인 파일 바이트, 불완전 기록 수, 현재 원본 복구 필요 여부와 런타임 누락 조각 수. 보고서는 생성 시점의 값이므로 `generatedAtMs`도 확인한다.

불완전 원본은 워치의 `capture-incomplete-<UUID>.json`과 그 JSON이 참조하는 남은 `.kcs.part` 조각으로 보존한다. JSON에는 세션/세트/시도 ID, 기대 샘플 수, 오류, 원래 런타임이 있다. 정상 완료 manifest를 만들지 않고 폰 자동 분석에도 넣지 않는다. 파일 삭제/앱 초기화로 정리하지 않는다. 정상 수집 상태에서 불완전 기록이 발생하면 원인을 조사한다. 누락됐던 파일을 되살리면 해당 시도의 복구를 다시 검사할 수 있다.

원본은 20바이트 헤더이며 샘플당 KCS v1은 40바이트, v2는 76바이트다. v2에 50Hz가 실제로 유지되면 압축 전 약 228KB/분, 60초 세트 30개는 약 6.8MB이다(영상 제외, 실측 용량이 아닌 형식 기반 계산). 심박도 레코드에 포함된다. 압축률은 움직임/타임스탬프에 따라 달라진다. 압축 후에도 원본 샘플을 복원할 수 있다.

Data Layer 정리는 캡처 ID의 정확한 경로에만 적용한다. `wear://*`와 `FILTER_LITERAL`/`FILTER_PREFIX`의 API 의미는 [Google DataClient 문서](https://developers.google.com/android/reference/com/google/android/gms/wearable/DataClient)를 기준으로 구현했다. 실제 기기간 전달/삭제 전파는 이 실기기 검증에서 확인해야 한다.
