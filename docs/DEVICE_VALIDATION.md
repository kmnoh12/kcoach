# 폰·워치 실기기 검증

2026-10-12: 연결된 ADB 기기 0개. 사용자가 현재 연결하기 어렵다고 답했으므로 아래 실기기 시나리오는 모두 **미실행**이다. Robolectric의 서비스 재생성 검사는 실제 화면 꺼짐·Bluetooth·Doze·기기 재부팅 검사를 대신하지 않는다.

## 연결 전 준비

프로젝트 루트에서 다음 명령으로 기기 목록, 설치 APK 일치 여부와 저장 용량 보고서를 읽는다.

```sh
python3 tools/device_check.py
```

도구는 설치·실행·종료·설정 변경을 하지 않는다. 기본 비교 대상은 현재 폰/워치 debug APK이다. 다른 빌드를 검증할 때는 `--phone-apk`와 `--wear-apk`로 해당 파일을 지정한다. 버전명만 같아도 코드가 다를 수 있으므로 SHA-256도 비교한다. APK를 읽을 수 없거나 split APK이면 일치 여부는 확인 불가이다.

실물 폰과 워치가 모두 ADB에 연결되고 승인되어야 사전 검사가 통과한다. 워치는 `android.hardware.type.watch` 기능으로 구분한다. Bluetooth 켜짐은 Data Layer 통신 성공의 증거가 아니다. 그래서 도구는 항상 `dataLayerLink=NOT_VERIFIED`, `hardwareScenarios=NOT_RUN`으로 출력한다. 종료 코드 2는 미연결/확인 불가를 포함한 사전 조건 미충족이다.

새 ID/SYNC/ACK 규약을 검사하려면 폰과 워치 모두 이번 코드로 빌드한 앱이어야 한다. 설치/업데이트와 배포는 별도로 다룬다. `tools/release.sh`와 git push는 사용자가 “올려”라고 할 때만 실행한다.

## 실기기 시나리오

| 순서 | 조작 | 확인할 결과 | 상태 |
|---|---|---|---|
| 1 | 폰에서 운동 시작, 워치에서 센서 기록·반복 수 확인 | 같은 세션/세트/시도 ID, 실제 측정된 심박만 표시 | 미실행 |
| 2 | 폰 화면을 끄고 워치에서 세트 완료, 휴식 만료까지 유지 | 완료 저장·휴식·다음 세트 진행, 화면 복귀 후 중복 완료 없음 | 미실행 |
| 3 | 운동 중 연결을 끊고 워치에서 완료, 연결 복구 | 워치의 반복/센서 기록 유지, 완료 ACK까지 재전송, 폰에 한 번만 반영 | 미실행 |
| 4 | 세트 삭제·되돌리기, 같은 세트 완료 취소 후 다시 측정 | 표시 번호가 바뀌어도 같은 세트 유지, 이전 시도 결과는 새 수행값을 보정하지 않음 | 미실행 |
| 5 | 같은 운동을 두 위치에 넣고 번갈아 선택 | 각 위치의 세트 선택과 반복 수가 서로 섞이지 않음 | 미실행 |
| 6 | 폰 앱을 실제로 종료한 동안 워치가 센서 기록 전송, 폰 앱을 다시 직접 실행 | 기존 DataItem도 다시 읽어 원본 저장 후 ACK, 분석 복구 및 완료 기록 보정 | 미실행 |
| 7 | 일시정지·휴식 중 워치 서비스 재생성, 이어서 별도로 워치 전체 재부팅 | 체크포인트에 저장된 반복·센서 조각·휴식 상태 복원, 폰 SYNC 후 일치 | 미실행 |
| 8 | 완료 기록 저장 후 늦게 네이티브 분석 완료 | 실제 수행 횟수·볼륨·이력 수정, 사용자 수동 입력 유지, 같은 날 다른 운동 보존 | 미실행 |
| 9 | ACK 후 연결 끊김/복구, 다음 운동 종료까지 유지 | 워치 전송 사본·DataItem 정리 재시도, 폰 원본과 분석 보존, 대기 중 불필요한 heartbeat 종료 | 미실행 |
| 10 | 여러 운동 후 용량 보고서 수집 | 폰 `missingFiles=0`, 워치 `missingQueuedFiles=0`, `missingRuntimeChunks=0`, `captureRecoveryRequired=false`, 전송 대기 해소, 실패 원본 보존. `incompleteCaptures>0`이면 격리 기록 사유를 확인 | 미실행 |

`force-stop`은 단순 프로세스 종료와 다르다. 강제 중지된 앱이 사용자가 다시 열기 전까지 자동으로 깨어나는 것을 합격 조건으로 삼지 않는다. 기기 재부팅과 Robolectric 서비스 재생성도 별도 항목이다. 종료 직전 체크포인트에 포함되지 않은 샘플/미완료 동작은 보장하지 않는다.

## 기록과 판정

각 시나리오에 폰/워치 모델·OS, 설치 APK SHA-256, 실제 조작 시각, sessionId/setId/attemptId/captureId와 관찰 결과를 기록한다. 실패 시 로그의 `KCoachEvent`와 앱 저장 상태를 함께 비교한다. 로그만으로 화면 동작이나 Bluetooth 복귀를 통과 처리하지 않는다. 배터리 평가는 시작/종료 잔량과 동일 시간·조건을 함께 남긴다. 현재는 실제 기기의 소모량을 측정하지 않았다.

debug 앱은 `run-as dev.kyungmin.kcoach cat files/capture-storage.json`으로 보고서를 읽을 수 있다. OTA 앱은 debuggable=false이므로 읽을 수 없으면 도구가 `UNAVAILABLE`로 표시한다. 데이터 삭제/앱 초기화로 검증 문제를 숨기지 않는다.

폰 보고서: 센서 기록 수, 전체 파일 바이트, 실패·미확인 기록 수, 누락 파일, 참조되지 않은 파일, 완료 snapshot 용량 추정. 워치 보고서: 전송 대기 수, 누락 원본/manifest, DataItem 정리 대기 수, 전체/미확인 파일 바이트, 불완전 기록 수, 현재 원본 복구 필요 여부와 런타임 누락 조각 수. 보고서는 생성 시점의 값이므로 `generatedAtMs`도 확인한다.

불완전 원본은 워치의 `capture-incomplete-<UUID>.json`과 그 JSON이 참조하는 남은 `.kcs.part` 조각으로 보존한다. JSON에는 세션/세트/시도 ID, 기대 샘플 수, 오류, 원래 런타임이 있다. 정상 완료 manifest를 만들지 않고 폰 자동 분석에도 넣지 않는다. 파일 삭제/앱 초기화로 정리하지 않는다. 정상 수집 상태에서 불완전 기록이 발생하면 원인을 조사한다. 누락됐던 파일을 되살리면 해당 시도의 복구를 다시 검사할 수 있다.

원본 형식은 20바이트 헤더 + 샘플당 40바이트이다. 50Hz가 실제로 유지되었다면 압축 전 약 120KB/분, 60초 세트 30개는 약 3.6MB이다(실측 용량이 아닌 형식 기반 계산). 심박도 레코드에 포함된다. 압축률은 움직임/타임스탬프에 따라 달라진다. 자동 삭제나 완료 snapshot 보존 기한은 도입하지 않았다. 압축 후에도 모든 원본 샘플을 복원할 수 있다. 워치의 기존 기록 상한은 한 세트 60,000샘플이다.

Data Layer 정리는 캡처 ID의 정확한 경로에만 적용한다. `wear://*`와 `FILTER_LITERAL`/`FILTER_PREFIX`의 API 의미는 [Google DataClient 문서](https://developers.google.com/android/reference/com/google/android/gms/wearable/DataClient)를 기준으로 구현했다. 실제 기기간 전달/삭제 전파는 이 실기기 검증에서 확인해야 한다.
