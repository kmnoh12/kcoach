# 2~5단계 조사 (2026-10-11)

1단계 실측 전에 미리 알아둘 것들. 실측 결과가 나오면 2단계 결정에 바로 쓴다.

## 2단계: 측정 방식

### 시장 현실
- Garmin 기본 반복 카운트는 머신, 벤치, 스쿼트에서 자주 틀리고 수동 수정이 필요하다는 평가. 손목이 크게 움직이는 덤벨 컬, 숄더프레스에서 그나마 낫다.
- Apple Watch는 맞춤 앱으로 한 검증 연구에서 반복 카운트 오차 0.92%. 기본 기능이 아니라 연구용 앱 기준.
- Samsung은 근거 자료가 거의 없음.
- 결론: "반복 카운트" 자체로는 차별화가 어렵고, 개인 맞춤과 속도 분석이 차별점.

### 개인 맞춤 카운팅
- few-shot 메트릭 학습: 처음 보는 운동 28종에서 10회 이상 세트를 정확히 센 확률 86.8%.
- WeakCounterF: 구간 경계 없이 "이 세트는 몇 회" 같은 약한 라벨만으로 학습.
- **KCoach 적용**: 사용자가 세트마다 실제 횟수를 입력하면 그게 그대로 약한 라벨이 된다. 운동할수록 데이터가 쌓이는 구조.

### 속도
- Apple Watch 손목 착용 평균 속도: 스쿼트에서 모션캡처 대비 r = 0.95~0.97. 바벨 부착 센서와 비슷한 수준. 스쿼트만 검증됨.
- **KCoach 적용**: 반복별 평균 속도와 세트 내 속도 감소율. 속도 감소로 남은 반복(RIR)을 추정하는 건 VBT 쪽 가설이라 실측으로 검증 필요.

### 센서 경로
- Samsung Health Sensor SDK도 가속도 연속 추적을 지원하지만 배포에는 삼성 파트너 승인이 필요하다. 지금처럼 SensorManager를 유지.

## 3단계: 구조

- 운동 중에는 Ongoing Activity가 필수다(Wear OS 품질 가이드 WO-V4). 갤럭시 워치8의 Now Bar도 이걸로 표시되고, 탭하면 운동 화면으로 돌아와야 한다.
- Wear OS 6: 앰비언트 모드에서도 맨 위 액티비티가 resumed로 남는다. 앰비언트 화면은 최소로, 1~2분에 한 번 이상 깨우지 않기.
- Health Services(심박수)는 화면 꺼짐/앰비언트에서 데이터를 몰아서 준다. 심박수는 실시간 표시용이 아니라 기록용으로 본다.
- targetSdk 36으로 올리면 심박 권한이 `health.READ_HEART_RATE`로 바뀐다(BODY_SENSORS는 maxSdk 35). 지금은 35라 당장 영향 없음.
- Android 16: 포그라운드 서비스에서 띄운 백그라운드 작업도 실행 할당량을 받는다.
- **KCoach 적용**: 폰이 세션 상태의 단일 원본, 워치는 센서 스트림 + 로컬 버퍼 + 화면용 사본. 통신은 상태 변경만 메시지로, 센서는 채널 스트림으로(1단계에서 이미 구현).
- UI 기술: Wear는 Compose for Wear OS Material 3(1.5.0 안정판)가 공식 권장. 폰도 Compose로 통일하면 4,000줄 단일 파일을 화면별로 나누기 쉬움.

## 4단계: 디자인

- 플릭: 운동일지·루틴 앱, 애플워치만 지원(Wear OS 미지원).
- Strong과 Hevy 비교에서 공통으로 꼽히는 것:
  - 세트 사이에 숨찬 상태로 빠르게 기록해야 한다 → 속도가 최우선.
  - 지난번 중량과 횟수를 미리 채워두고 확인만 누르게.
  - 세트 완료 시 휴식 타이머 자동 시작(Strong 방식).
  - 운동 중 화면은 미니멀하게.
- 워치는 Material 3 Expressive 가이드를 따른다.
- 남은 결정: Kyungmin이 레퍼런스 앱이나 스크린샷을 고른다.

## 5단계: 기능

### 다음 운동 목표(점진적 과부하)
- 업계 표준은 더블 프로그레션. 반복 범위 안에서 횟수를 늘리다가 모든 세트가 상한에 닿으면 중량을 올린다(Hevy Trainer 방식).
- RIR 입력은 선택. Alpha Progression은 RIR 없이 기록만으로 추천한다.
- KCoach만의 차별점 후보: 손목 속도 감소를 자동 노력 신호로 쓰기(2단계 검증 후).

### 마이마운틴 칼로리
- ACSM 걷기 공식: VO2 = 0.1·S + 1.8·S·G + 3.5 (S: m/min, G: 경사 소수).
- 검증 범위는 대략 시속 3.2~5.6km, 경사 15%까지. 그 이상 경사는 정확도를 보장 못 함.
- 손잡이를 잡으면 과대 추정된다.
- 이미 `core/InclineEnergyEstimator.kt`가 있으니 범위 밖 경고와 손잡이 여부만 추가 검토.

## 부록: MM-Fit 오프라인 검증 (2026-10-11)

공개 데이터셋 MM-Fit(왼손 스마트워치 100Hz, 616세트, 세트별 정답 반복수)에 `WristTrajectoryTracker`를 그대로 돌렸다.
재현: `python3 -I tools/mmfit_convert.py <mm-fit> work/datasets/mmfit-probe` 후 `KCOACH_MMFIT_DIR=work/datasets/mmfit-probe gradle :core:test -PcoreOnly` → `core/build/mmfit-report.txt`.

발견:
1. 연속 반복에는 멈춤이 거의 없다(트라이셉 익스텐션 세트 중 정지 4%, 최장 0.19초). 정지 기준만으로는 반복을 하나도 못 나눴다 → 이동 축 속도의 방향 전환에서도 구간을 나누도록 변경.
2. 운동 중 자이로만으로 자세를 추정하면 세트 하나 동안 약 20° 기울어 중력이 직선 가속으로 새어 들어온다(약 3 m/s²) → 움직이는 중에도 약한 중력 보정 + 가속도의 느린 평균 제거.
3. 방향 전환 기준은 직전 움직임 크기의 40% 이상일 때만 인정(필터 언더슈트 오검출 방지), 전환 직후 작고 짧게 멈추는 꼬리 구간은 앞 구간과 합쳐 다시 계산.

결과(구간 2개 = 반복 1회로 셌을 때, ±1회 이내 세트 비율):

| 운동 | ±1회 이내 | 평균 오차 |
|---|---|---|
| 레터럴 레이즈 | 96% | 0.57회 |
| 트라이셉 익스텐션 | 91% | 0.69회 |
| 덤벨 로우 | 88% | 0.88회 |
| 스쿼트 | 88% | 0.91회 |
| 싯업 | 86% | 0.86회 |
| 덤벨 숄더프레스 | 57% | 2.05회 |
| 런지 | 55% | 1.73회 |
| 바이셉 컬 | 41% | 2.86회 (구간 1개 = 1회로 셀 때) |
| 푸시업 | 0% | 손이 바닥에 고정돼 손목이 거의 안 움직임 |

시도했다가 되돌린 것: 회전 속도 기반 방향 전환(컬 개선 목적) → 컬 29%로 오히려 악화, 다른 운동도 소폭 하락.
남은 과제: 컬·숄더프레스는 실측 데이터로 원인 확인. 이 데이터셋은 맨몸·덤벨 위주라 머신 운동 검증은 Kyungmin 실측이 필요.
